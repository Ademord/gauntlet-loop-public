# Frozen behavior requirements for the proposed Gauntlet release

Version: 1. Baseline: public Gauntlet 5.2.0, commit `17161321b3cd1603ae7b5d710e3e85a837331cb8`.

These cases were authored without reading a 5.3 candidate. They test the requested extension and retention of 5.2 behavior. They do not establish comparative performance, complete runtime enforcement, or optimal topology. All data and actions are synthetic. This directory is independent acceptance material; the candidate author must not edit it to obtain a pass.

## Source of the bar

The requested release scope is action-scoped evidence eligibility beyond a matching hash; current actionable obligations on return/resume; required shared-state invariants after delivery; and optional diagnosis/evaluation provenance that distinguishes final-development-selected versions from best-on-held-out results. No new authority, permanent agents, mandatory harness, or paid study is authorized by this acceptance package.

Existing 5.2 requirements already demand versioned criteria and authority, independent acceptance against the actual candidate, preservation of HOLDs, scope-bounded work, small useful teams, verified selected delivery surfaces, budget continuity and explicit resume validation. ## Requirements

**R1 — Evaluate an evidence use, not just an evidence item.** A receipt can support one action or historical claim while being ineligible for another. Before using it for present acceptance or a consequential action, establish that its relevant artifact inputs, governing requirement, scope, authorization, lifecycle and selection conditions match that use. Apply only conditions material to the action; do not require irrelevant fields universally. Unknown material eligibility is not permission or successful acceptance. Unchanged bytes alone do not prove unchanged applicability.

**R2 — Keep useful work possible.** Missing acceptance evidence does not automatically prohibit authorized, harmless inspection, diagnosis, preparation or revalidation. A blocked surface does not block independent authorized obligations. Every withheld claim/action should name the smallest useful next observation or dependency; do not demand unrelated approvals or infrastructure.

**R3 — Retain history truthfully.** Valid historical evidence remains available for a scoped historical answer when it is no longer eligible for current acceptance. Distinguish the old assertion from present state, and retain failed/superseded evidence and its disposition. Do not erase history to simplify current status.

**R4 — Restore the current obligations, not just the old checkpoint.** A returned worker or resumed lead must account for compatible user additions, invalidating corrections, outstanding commitments, relevant HOLDs and uncertain effects before dispatch. Revalidate only affected claims where independence is established. Carry forward used budgets and review lineage; a fresh worker/session does not reset them.

**R5 — Verify required shared-state outcomes.** Where the actual task requires preserving rows, metadata, indexes, configuration or other shared state, delivery acceptance must cover those invariants and the affected complete journey. A correct output file or old receipt does not prove that required surrounding state remains correct. This is task-scoped: ordinary low-impact edits do not imply a universal whole-system audit.

**R6 — Count independent support honestly.** Reposts, summaries, copied receipts and several agents reading the same original are not separate observations. An explicit current independent check or discriminating observation can resolve a material dispute. Repeated correlated opinion cannot silently resolve it or erase a HOLD.

**R7 — Preserve optionality and scope.** A routine low-impact correction can use the light topology and proportional ordinary verification. The release must not require runtime traces, repeated trials, a new database, a fixed vendor pairing, a fixed large headcount or a research campaign on every task. Any diagnostic protocol belongs to selected method-improvement work, not as a precondition to ordinary delivery.

**R8 — Report selection and measurement honestly.** If a harness candidate is selected using development results, distinguish its later frozen held-out measurement from a different candidate selected for the best held-out score. Identify historical versus fresh controls, actual compared identities, denominator and missing trials. Do not convert an incomplete grid, a lower flipping rate, or an aggregate improvement with known regressions into unsupported general success. Recorded implementation conformance, end-task scores and true operational enforcement are separate claims.

## How to execute and score

`scenarios.json` is the frozen input set. It includes valid controls and adversarial cases. `oracle.json` states the decision observations for each case without requiring any literal wording. Feed a scenario's `input` and `request` to the candidate workflow; preserve its action plan, evidence uses and final report. For an implementation, substitute synthetic tool adapters and record actual calls and final state. For a Markdown-only skill, run a bounded scenario simulation and mark the result as a simulated decision, not live enforcement.

A pass requires all specified observable decisions: an ineligible consequential action must not occur, a supported valid control must not be gratuitously blocked, and material current obligations must be present in the plan. Citing this document or repeating its vocabulary is not proof. Scores must cite the actual decision/evidence/state output; an evaluator cannot award a pass solely because a rule is written in the candidate. Do not silently reinterpret a contradictory output as the intended action. Ask for no real external writes during scenarios.

Retain original outputs and failed cases. If the fixture itself is wrong, preserve it and record an independently justified oracle amendment before rescoring. The package may be frozen and copied into a sanitized public run record by the lead; these files should otherwise remain untouched during candidate repair.

The 16 scenarios are bounded acceptance fixtures, not statistical samples. Passing them supports the scoped behavior exercised; it does not measure real-task success, cost savings, universal evidence quality or automatic enforcement.

## Optional implementation interface

An implementation may expose `assess_use(evidence, proposed_use, current_context)` returning `eligible`, `ineligible` or `unknown`, plus material unmet conditions and permitted next observations. `proposed_use` must distinguish historical reporting, investigation, current acceptance and a consequential action. No particular programming language or field spelling is required. A receipt's historical validity and its eligibility for the proposed use should be separate results.

A workflow simulation can return an action plan, evidence-to-claim references, remaining obligations, and preserved budget state. This makes the oracle inspectable, but does not replace execution evidence: saying an action is withheld while also dispatching it fails. The package prescribes outcomes, not a new runtime, database or autonomous authority.
