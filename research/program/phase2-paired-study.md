# Phase 2: paired study protocol (pre-registration draft, 17 September 2026)

Status: designed, not run. The owner answered the phase-2 gate question on 17 September 2026: willing to pay for paired runs where there is value. This document fixes the design before any pair runs so that the analysis cannot be bent to the result. Changes after the first pair runs are recorded as amendments with a date and reason.

## 1. Why pairs, and what each result would change

An observational ledger (phase 0) can only show associations confounded by the lead's own choices. A pair runs the same task twice with one flag flipped, so the task, the models, the checks, and the critic are held constant and only the flag varies. The unit of value is a default that applies to every future run. The candidate flags, ranked by expected value:

| # | Flag | Arm A | Arm B | Primary outcome | If A better | If B better | If no difference |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F1 | `light` topology on low-difficulty deterministic tasks | light: one build, one evidence-based review | compact: build, critic, comparison loop | accepted within budget; reviews used | keep `light` gate as is | tighten or remove the `light` gate | keep `light` (cheaper at equal acceptance) |
| F2 | Evidence ladder | ladder on (judgment advisory from round 3) | ladder off (any class may force revision every round) | reviews used to acceptance; acceptance rate; drift findings | keep ladder | revert ladder to advisory-only text | keep ladder (no cost, no harm) |
| F3 | Critic shape | three parallel lens critics per round | one generalist critic per round | acceptance rate; defects missed (held-out check); reviews used | keep parallel lenses as default for `high` | make single critic the default | choose by cost |
| F4 | Lesson retrieval | learning on, three-lesson allowance | learning on, no retrieval (lessons recorded, never injected) | reviews used; repeated known failures | keep allowance | drop retrieval, keep the ledger | drop retrieval |

F1 and F2 come first: they are the two v5 changes that alter what happens on every run, they are cheapest to test (F1 needs only low-difficulty deterministic tasks; F2 needs tasks that reach round 3), and each has a clear decision attached. F4 requires an existing lesson corpus and is deferred until one exists.

## 2. Task pool

Tasks are minted from the owner's own repositories so that outcomes are deterministic and relevant:

- Revert-fix tasks: a commit that fixed a bug and touched a test. Revert the fix, keep the test; the task is "make the failing test pass without breaking the suite". Ground truth is the original fix; a held-out check is the full suite plus, where possible, one additional test written from the original commit's intent and not shown to the builder.
- Small feature tasks: a commit that added a small feature with tests, reverted the same way.
- Inclusion: offline test suite, test command under two minutes, diff under about 80 changed lines, no personal or client data in the repository, repository size manageable in a worktree.
- Exclusion: anything under a directory the owner has marked private, any repository named as a client project, any task whose test depends on a network or a browser.

The survey of candidate repositories and commits is kept next to this file (`paired-study/task-pool-survey-<date>.md`, generated by `tools/paired_study/survey_repos.py`) with a ranking and minting record. Each task gets a spec file (`tools/paired_study/task_spec.example.yaml` shows the shape) with its base commit, answer commit, the test files copied from the answer, any held-out files, an optional offline setup command, test command, failing tests, difficulty estimate with proxies, and verifiability class. Difficulty for F1 tasks must be `low` by the proxies before the run, recorded in the spec, never adjusted after.

Amendment, 18 September 2026: the first survey found the natural pool thin (two mintable commits out of seventeen; the rest are release-sized). Two tasks were minted and checked empirically (`paired-study/tasks/`). For the F1 volume, mutation-minted tasks (one semantic mutation of a test-covered function; the original is the answer) are the supply, with the stated limit that they generalize only to the low-difficulty deterministic class and cannot exercise F2. Medium tasks for F2 must be cut by a person from release commits. Held-out tests may be study-owned files copied into the clone after acceptance, since the answer commit often has none.

## 3. Design

- Within-task pairs: every task runs once under arm A and once under arm B. Order is counterbalanced by the parity of the task ID hash and recorded.
- Isolation: each arm runs in its own git worktree from the same base commit; nothing from one arm is visible to the other.
- Constants: same model IDs for lead, builder, and critic across both arms, recorded per run; same skill version (5.0.0) with the flag as the only prompt difference; same checks, frozen in the task spec.
- Blinding: the critic prompt is identical across arms and does not mention an experiment or a flag. The lead prompt differs only in the flag sentences generated by `tools/paired_study/make_arms.py`; the diff between the two prompts is committed with the pair so the difference is inspectable.
- Budget: a user cap per run fixed in the spec (default 8 reviews, reserve 2), identical across arms.
- Runner: `tools/paired_study/run_pair.py` generates both prompts and, in execute mode, launches each arm as a headless agent session in its worktree and collects the milestone record. Execute mode is documented but untested at the time of writing; the first pair is the harness test.

## 4. Outcomes

Primary, per arm, deterministic: `accepted` (all required checks pass on the integrated worktree by an independent rerun of the test command), `reviews_used`, `subagent_tokens` (harness-reported, or unknown), `wall_clock_s`. Secondary: held-out test result (defect missed or not), number of advisory-only findings, number of drift findings, whether the run parked.

## 5. Sample size and sequential looks

Target 30 pairs per flag. Analyze at 10, 20, and 30 pairs. Because there are three looks, each uses a two-sided alpha of 0.05 / 3 (Bonferroni) for the primary outcomes. Stop early only if a primary outcome crosses that threshold or if the harness proves unusable (more than a third of pairs invalid for reasons unrelated to the flag).

## 6. Analysis (implemented in `tools/paired_study/analyze_pairs.py`)

- Acceptance: exact binomial test on discordant pairs (McNemar's exact form).
- Reviews used, tokens, wall clock: paired differences with an exact sign test and a bootstrap 95% confidence interval of the mean difference (10,000 resamples, seeded).
- Report both the estimate and the interval; a result with an interval that includes zero is "no difference detected", not "no effect".
- Pairs where either arm failed for a harness reason (crash, quota, worktree error) are excluded and counted; the count is reported.

## 7. Guards

- Checks and difficulty are fixed in the spec before either arm runs; the runner refuses a spec edited after its first arm ran (spec hash recorded in the pair manifest).
- The critic never sees the flag; the builder never sees the held-out test.
- The analysis script is committed before the first pair runs; changes to it after that are amendments.
- The owner, not an agent, decides what a result changes in the skill, through the backlog and the bounded workflow-improvement process.

## 8. Cost

Per pair: two runs. Cost anchors come from the ledger: the one fully recorded research run used about 4.2M subagent tokens over 2 h 25 min; a small code-fix run is expected to be far smaller (ASSUMPTION: 100k to 400k subagent tokens and 10 to 30 minutes per arm; the first pair measures this). At the assumed size, 30 pairs of F1 cost on the order of 6M to 24M subagent tokens, comparable to a week or two of the owner's ordinary gauntlet use. F3 is dearer because arm A runs three critics per round.

## 9. Predictions, stated before running

- F1: acceptance equal within a few points; reviews used lower under `light` by about one review per task. Confidence: moderate.
- F2: on tasks that reach round 3, reviews used lower with the ladder; acceptance equal; drift findings lower. On tasks accepted within two rounds, no difference. Confidence: low; most small deterministic tasks will not reach round 3, which is itself a finding about where the ladder matters.
- F3: acceptance equal on deterministic tasks; parallel lenses catch more held-out defects on `high` tasks only. Confidence: low.

## 10. Reporting

Each look produces a short Markdown report from the analysis script under `research/program/paired-study/`, with the pair manifests, prompt diffs, and per-run milestone lines. Results enter the skill only through the backlog. A result is reported with its interval, its exclusions, and the sentence "on tasks of this class, from this owner's repositories, with these model versions".

## Amendment, 19 September 2026: harness isolation, measurement, and mutation tasks

Recorded before any valid pair has run; the first attempt failed at startup and produced no task work (see `paired-study/LOG.md`).

- **Isolation.** Each arm is a headless `claude -p` session in a fresh clone under the system temporary directory, outside any repository, with `--setting-sources project,local --strict-mcp-config --disable-slash-commands`: no user-level hooks, plugins, MCP servers, or skills reach an arm. Both arms use the same pinned model (`claude-sonnet-5` unless a pair records otherwise), permission mode `acceptEdits`, and the same tool allowlist. A preflight call confirms the CLI is logged in before anything is cloned.
- **Acceptance.** `accepted` means the independent rerun of the test command passes after every tracked file under the protected test paths has been restored to the task base, and no file outside the allowed paths changed (new test files are allowed). The agent's own declared state is recorded but does not decide acceptance.
- **Cost and effort.** `cost_usd` and `total_tokens` come from the transcript's final result event; `reviews_used` is the agent's recorded review count when it writes an integer, otherwise the number of critic dispatches counted in the transcript. These replace the earlier `subagent_tokens` outcome.
- **Mutation-minted tasks.** For the F1 volume, tasks are also minted by applying one semantic mutation (a flipped comparison, swapped `and`/`or`, a dropped `not`, a changed small integer or boolean literal) to a test-covered line and keeping it only if exactly one or two tests fail; the original line is the answer (`tools/paired_study/mint_mutations.py`). Their results generalize only to one-token defects in the minted repository, and they cannot exercise F2.
- **Startup failures.** A pair stops when an arm fails at startup, and such rows are marked `harness_failure` with a reason; section 6 already excludes them from analysis.
